# Generating our own Termix API spec: strategy, sources and pipeline

This document explains why termix-sdk does not consume the official Termix `openapi.json`, and how we derive our own spec by mining the Termix backend source code. It records the decisions taken, the evidence behind them, and the extraction pipeline phase by phase.

Everything marked "confirmed" below was verified against the tag `release-2.7.1-tag` (commit `76fd9ee`), the latest published release at the time of writing.

## Background: why the official spec is not enough

The official spec (`docs.termix.site/api/termix-api`) is generated by [`swagger-jsdoc`](https://www.npmjs.com/package/swagger-jsdoc) from hand-written `/** @openapi ... */` comments above each route. Nothing validates those comments against the code, and the glob it scans does not even include `database/database.ts` or the top-level `automations/` folder. Two audits of the [Termix-SSH/Termix](https://github.com/Termix-SSH/Termix) source led to the decision documented here:

- **Coverage.** The official spec lists 413 unique method+path pairs. The backend registers about 470. Roughly 80 real endpoints are missing, including whole features: the file manager trash, the tmux monitor, wake-on-LAN, database export/import, host metrics managers.
- **Schemas.** Of 1157 response objects in the official spec, only 19 (1.6%) declare a schema. Of 220 POST/PUT/PATCH operations, 55 declare no request body at all, and the ones that do are often incomplete (`POST /host/db/host` reads about 95 body fields, none documented; `POST /users/login` accepts an undocumented `rememberMe` and returns two different 200 shapes).
- **Auth.** The spec declares one security scheme (bearer JWT). The middleware accepts three: the `jwt` cookie, `Authorization: Bearer <JWT>`, and `Authorization: Bearer tmx_<api key>`.

The conclusion: the official spec is useful to locate where a feature lives, but it cannot be the source of truth for what exists or for request/response types.

## What "complete spec" means for us

For every HTTP endpoint of the backend, the generated spec must state:

| Item | Source | Example (`POST /host/db/host`) |
|---|---|---|
| Method + final path (mount prefixes resolved) | `app.use` / `router.use` / `registerXRoutes` graph | `POST /host/db/host` and `POST /host/enroll` (same handler) |
| Service and port serving the path | which `express()` the route hangs from | `database.ts`, port 30001 |
| Required authentication and level | middleware chain on the route + global `app.use` | `authenticateJWT` + `requireDataAccess` + `requireHostEnrollmentAccessForPath` |
| Path parameters, typed | `:id` in the path + how `req.params.id` is coerced | `Number(req.params.id)` becomes integer |
| Query parameters, typed, with required flag | `req.query.x` + coercion (`as string`, `Number()`, `=== "true"`) | `?includeCredentials=true` becomes boolean |
| Relevant headers | `req.headers["x-..."]`, `req.get("User-Agent")` | `X-Electron-App`, `User-Agent: Termix-Mobile/` |
| Body content type and schema | `express.json` / `multer` / `busboy` / `express.raw` + `req.body` destructuring | JSON with ~95 fields, or `multipart/form-data` with `key` (file) + `data` (JSON string) |
| Every response, per status code, with schema | each `res.status(N).json(expr)` / `res.json(expr)` + type of `expr` | 200 sanitized `Host`, 400 `{error}`, 403 `{error}`, 500 `{error}` |
| Non-JSON responses | `res.send`, `res.redirect`, `res.sendFile`, `Content-Disposition`, `text/event-stream` | `application/octet-stream` download, SSE, OAuth 302 redirect |
| Real examples | test assertions + frontend client types | `expect(res.statusCode).toBe(423)` |
| Confidence of each schema | which source produced it | `x-confidence: repository-type` |

WebSocket endpoints (terminal, docker console, serial, c2s relay) are not HTTP and do not fit in `paths`, but they go into the spec as an extension (`x-websocket-endpoints`) because the SDK will need them.

## Real backend topology (confirmed)

The backend is not a single server. `starter.ts` imports and starts **8 Express apps** and **4 WebSocket servers**, each on its own port. The official spec lists 7 `servers` and not all of them match.

| Service | File | Port | Global auth (`app.use(createAuthMiddleware())`) | Body limit |
|---|---|---|---|---|
| Main (DB, users, hosts, everything under `database/routes/*`, `ai/`, `automations`) | `database/database.ts` | 30001 (HTTP) + optional SSL port | **No**: auth is per route (explicit `authenticateJWT` on each `router.METHOD`) | `json` 1gb, `urlencoded` 1gb, `raw` 5gb (`application/octet-stream`) |
| Tunnel | `hosts/tunnel/index.ts` | 30003 | per route | 1mb |
| File manager | `hosts/file-manager/index.ts` | 30004 | **Yes** (line 133) | `raw` 5gb |
| Metrics / status / managers | `hosts/metrics/index.ts` | 30005 | **Yes**, except `POST /internal/login-alert`, registered before the middleware | 1mb |
| Dashboard | `services/dashboard.ts` | 30006 | Yes | 1mb |
| Docker | `hosts/docker/index.ts` | 30007 | Yes | 100mb |
| tmux monitor | `hosts/tmux/index.ts` | 30010 | per route | 1mb |
| Homepage | `services/homepage.ts` | 30012, bound to `127.0.0.1` only | Yes | 1mb |

WebSocket: terminal on `30002`, docker console on `30009`, serial on `30011`, and the tunnel c2s relay shares the HTTP server on 30003 at path `/ssh/tunnel/c2s/stream`.

This matters for the spec for two reasons: (1) each `path` must carry which server it lives on (we use per-operation `servers` + `x-termix-service`), and (2) the auth rule differs per app: on services with a global `app.use(auth)`, every route requires a token even without `authenticateJWT` in its signature, and registration order matters (`/internal/login-alert` is public only because it comes before the `app.use`).

## Available sources of ground truth (by reliability)

Order revised after inspecting the tag. The most important change from an earlier draft: **the repository layer is the primary source of response types**, not the Drizzle schema directly.

1. **Backend test suite** (`src/backend/tests/`, 206 `*.test.ts` files, vitest). Validated behavior. Route tests (`tests/database/routes/*.test.ts`, 33 files) do not use supertest: they import the router, locate the handler through `router.stack`, call it with mocked `req`/`res` (a `makeRes()` that captures `statusCode` and `body`), and assert `res.statusCode` and `res.body` with `toEqual`/`toMatchObject`. They cover only a fraction of the routes, but where they exist they are exact examples.
2. **Typed repositories** (`src/backend/database/repositories/*.ts`, 60 files). Almost every handler does `res.json(await createCurrentXRepository().method(...))`. Those methods have declared return types (`Promise<SnippetFolderRecord[]>`, `Promise<string[]>`, etc.), and the `*Record` types are `typeof table.$inferSelect` from Drizzle (85 occurrences). In other words: the response type is declared in TypeScript and can be derived mechanically with the type checker.
3. **Drizzle schema** (`src/backend/database/db/schema.ts`, 72 tables, canonical: `schema.mysql.ts`/`schema.pg.ts` are generated from it by `scripts/generate-dialect-schema.cjs`). Defines column name, type, `notNull`, `default`, foreign keys. It is the base of the `*Record` types and becomes `components.schemas`.
4. **Response transformers** (`database/routes/host-normalizers.ts`: `transformHostResponse`, `stripSensitiveFields`, `sanitizeHostForRecipient`; plus `serialize`, `toPublicSettings`, `formatCredentialOutput`, etc.). When a handler passes the entity through one of these before `res.json`, the shape changes (`text` columns become arrays/objects via `JSON.parse`, booleans are coerced, sensitive fields are removed and replaced by `hasKey`/`hasPassword`/...). Needs specific handling, see Phase 4.
5. **Shared types** (`src/types/*.ts`, ~1100 lines in `index.ts`). `Host` is the response shape the frontend expects, `HostData` is the request shape. Handlers do not use them (they destructure `req.body` untyped), but they are the best human description of large request bodies and serve as a cross-check.
6. **Frontend HTTP client** (`src/ui/main-axios.ts`, 2294 lines, plus `src/ui/api/*.ts`, 41 files, 8006 lines). Each function does `xApi.post("/path", body)` with a typed parameter and a declared `Promise<Return>`. It is the only place where request and response appear typed side by side per route. It also reveals protocol details the backend does not make obvious (e.g. `createSSHHost` sends multipart with a `data` field holding a JSON string when the key is a file).
7. **Reading the handler** (`req.body`/`req.query`/`req.params` + every `res.json()`). Still the source for request bodies (there is no Zod, express-validator, drizzle-zod or anything similar: validation is manual with `isNonEmptyString`, 187 uses, and `validateX` helpers).
8. **Existing `@openapi` comments** (425 JSDoc blocks). Not usable as schema, but `summary`, `description` and `tags` are good and we reuse them as text. Our extraction always wins on conflict.
9. **Live instance** (optional, `docker/` in the repo). Closes whatever is left: real serialization, computed fields, responses passed straight through from external libraries (Docker Engine API, Proxmox).

## Decisions

### 1. Obtaining the Termix source: disposable clone of the latest release tag

The script resolves the latest tag (`GET /repos/Termix-SSH/Termix/releases/latest`, confirmed: `release-2.7.1-tag`), shallow-clones only that tag (`git clone --depth 1 --branch <tag>`) into a temporary folder, runs the extraction, and deletes the folder at the end. Tag and commit go into `info.version` / `x-termix-source` of the spec.

**Why**: a git submodule was rejected (it would bring an entire TypeScript project into a Python SDK repo), and so was pinning an arbitrary commit. The latest release is what runs in production for Termix users.

### 2. Extraction tool: Node.js + ts-morph, not regex

**Concrete evidence.** A regex-based extraction needed 3 rounds of fixes to reach 472/472 resolved routes (a feedback loop in auto-mounting, a collision between same-named functions in different files, a parameter name differing from the call site). A ts-morph prototype run on the same clone reached **0 unresolved routes without any of those fixes** and found routes the regex structurally could not see:

- `router.post(["/db/host", "/enroll"], ...)`: path as an **array literal**. This explains why `/host/enroll` had shown up as "documented but absent from the code" in the first audit.
- `router.use("/opkssh-chooser/:requestId", async (req, res) => {...})`: a route registered through `.use()` with an inline handler. The distinction is by the shape of the second argument (identifier = sub-router mount, function = method catch-all route).
- `` `/${pathPrefix}/heartbeat` `` with `pathPrefix = "metrics"` as the default of a destructured parameter: ts-morph resolves the symbol and recovers the real default value.

Total (prototype, same tag): **476 route registrations, 477 unique method+path pairs** (the regex version reached 472/469).

Beyond route discovery, ts-morph is indispensable in the later phases: only the `TypeChecker` can give the return type of `createCurrentSnippetRepository().listFolders(userId)` inside a `res.json(...)`.

**Update — the pipeline has since been implemented and actually run**: the generator described in this document was written (`tools/spec-gen/`, TypeScript + ts-morph) and run from scratch against the same tag, with `unresolved: 0`. The final count is **494 route registrations** (491 unique method+path pairs + 3 `X.use()` catch-all routes) — higher than the prototype's because the finished resolver also correctly captures `router.use("/host/opkssh-callback/:requestId", ...)`, one equivalent catch-all route in `file-manager/index.ts`, and 3 routes (`/metrics/heartbeat`, `/metrics/register-viewer`, `/metrics/unregister-viewer`) that only showed up after a fix described in "Implementation status" below, found by the diff against the official spec itself (Phase 10, criterion 4).

### 3. Output format: OpenAPI 3.1 generated from a versioned IR (intermediate JSON)

Two outputs, both committed to this repo:

- `spec/termix-*-ir.json` (three files in the actual implementation — `termix-routes-ir.json` from Phase 1, `termix-drizzle-ir.json` from Phase 5, `termix-analysis-ir.json` from Phases 2-4 — rather than a single `termix-ir.json` as originally planned here): intermediate representation, one entry per route/table, with everything extracted. This is what the Python SDK generator actually consumes, because it carries things OpenAPI does not express well (service/port, per-field confidence, one handler behind two paths).
- `spec/termix-openapi.json`: OpenAPI 3.1 generated from the IR. Used for validation with standard tooling, diffing against the official spec, and any external consumer.

**Why 3.1 and not 3.0.3 like the official one**: 3.1 uses full JSON Schema (`type: ["string", "null"]`, `const`, `$defs`), which makes nullable Drizzle columns and string enums straightforward to map.

## Extraction pipeline, phase by phase

Each phase reads the output of the previous one and enriches the IR. All of them run in a single ts-morph `Project` loaded with Termix's `tsconfig.node.json` (which includes `src/backend/**`, `src/types/**` and `src/ui/types/**`, and excludes tests). Note: that tsconfig has `strict: false` and `noImplicitAny: false`, so much of `req.body` is `any`; this is why the request phases rely on syntactic analysis plus coercions, not only on the type checker.

### Phase 0: bootstrap

1. Resolve the tag and shallow-clone into a temporary folder.
2. `npm ci --ignore-scripts` inside the clone (`node_modules` is needed for the type checker to resolve `express`, `drizzle-orm`, `multer`, `busboy`). `--ignore-scripts` skips the Electron and `better-sqlite3` patch `postinstall` steps.
3. Create the ts-morph `Project` pointing at `tsconfig.node.json`. Add `src/ui/main-axios.ts` and `src/ui/api/*.ts` to a second `Project` (they are not in the backend tsconfig and depend on frontend types).
4. Record in `meta`: tag, commit, date, Express version (5.2.x, relevant for path syntax), file counts.

### Phase 1: route discovery and prefix resolution

**Input**: every `.ts` under `src/backend` except `tests/`.

**What to capture** (each form was confirmed in the code):

| Form | Handling |
|---|---|
| `X.get/post/put/patch/delete/all("path", ...mw, handler)` where `X` is any variable initialized with `express()` or `Router()` | a route. Method comes from the call name. |
| First argument is an `ArrayLiteralExpression` (`["/db/host", "/enroll"]`) | expand into N routes pointing to the same handler; record `x-shared-handler` between them |
| First argument is a template literal with `${ident}` | resolve `ident` through its symbol: literal, `const`, or default of a destructured parameter |
| `X.use("/prefix", routerIdent)` | a mount edge in the graph: `prefix(X) + "/prefix"` becomes the prefix of everything in `routerIdent` |
| `X.use("/prefix", (req, res) => {...})` or `X.use("/prefix", namedFn)` | a route with method `*` (catch-all). Record `x-any-method: true` |
| `X.use(routerIdent)` without a path, or `X.use("/", routerIdent)` | a mount with prefix `""` (e.g. `app.use("/", alertRulesRoutes)` in `database.ts`) |
| `registerXRoutes(app \| router, deps)` | follow to the function declaration; its first parameter (any name: `app`, `router`) inherits the prefix of the argument passed at the call site. Confirmed in `database.ts` (`registerAuditLogRoutes`, `registerTailscaleRoutes`), `host.ts` (`registerHostInternalRoutes`, `registerHostOpksshRoutes`, `registerLDAPAuthRoutes`, `registerSSOProviderRoutes`), `file-manager/index.ts` (5 `registerFile*Routes` functions), `tunnel/index.ts`, `docker/index.ts` |
| Router imported under a non-conventional name (`homepageItemsRouter`, `dashboardServiceLinksRouter`) | resolved by indexing **any identifier whose initializer is `Router()`**, not just `router`/`app`. In the tag: 28 `router` + 7 named ones. This closes a gap an earlier prototype had with `homepage.ts`. |

**Prefix resolution**: build the graph (app, router, sub-router) and DFS from each `express()`. Each final route gets `service` (file of the root `express()`), `port` (the `PORT` or `HTTP_PORT` constant in the same file, resolved by symbol) and the full `path`. A route that reaches no `express()` goes to `unresolved[]`, and the build fails if that list is not empty (this is the "0 unresolved routes" criterion the prototype already meets).

**Path syntax**: Express 5 uses `path-to-regexp` v8. Confirmed that no Termix route uses wildcards, regex, optionals (`{...}`) or splats: only literals and `:param`. The OpenAPI conversion is `:id` to `{id}`. Keep an assert so this fails loudly if a future version introduces another syntax.

**Middleware chain**: record the identifiers between the path and the final handler, in order. This feeds Phase 2 (auth) and Phase 3 (multipart). Counts in the tag: `authenticateJWT` 88 explicit uses, `requireAdmin` 9, `requireDataAccess` (varies per file), `upload.single("key")` 2, `upload.single("file")` 2, `validateHostId`, `resolveHandle`, `caResolver`, `requireHostEnrollmentAccessForPath`.

**Output (IR)**:

```json
{
  "id": "host.ts#L126:POST:/host/db/host",
  "method": "POST",
  "path": "/host/db/host",
  "expressPath": "/db/host",
  "service": "database",
  "port": 30001,
  "file": "src/backend/database/routes/host.ts",
  "line": 126,
  "handlerKind": "inline-arrow",
  "middlewares": ["authenticateJWT", "requireDataAccess", "requireHostEnrollmentAccessForPath", "upload.single(\"key\")"],
  "sharedHandlerWith": ["host.ts#L126:POST:/host/enroll"]
}
```

### Phase 2: authentication, authorization and input parameters

**Auth per route.** Derivation rule:

- Route on a service with a global `app.use(createAuthMiddleware())` (metrics, dashboard, docker, homepage), registered **after** that `app.use` in the file: requires auth. Registered before: public (the `/internal/login-alert` case).
- Route with `authenticateJWT` in the chain: requires auth.
- `requireAdmin` in the chain or `createAdminMiddleware()`: `x-requires-admin: true`, adds a 403 `{error: "Admin access required"}` response.
- `requireDataAccess` (`createDataAccessMiddleware()`): adds 401 `{error: "Authentication required"}` and 423 `{error, code: "DATA_LOCKED"}`.
- None of the above: `security: []` (public endpoint: `/health`, `/version`, `/users/login`, `/users/registration-allowed`, etc.).

Every authenticated route inherits the responses the middleware can emit, confirmed at `auth-manager.ts:678`: 401 `{error: "Missing authentication token"}`, 401 `{error: "Invalid token"}`, 401 `{error: "TOTP verification required", code: "TOTP_REQUIRED"}`, 401 `{code: "SESSION_NOT_FOUND"}`, 401 `{code: "SESSION_EXPIRED"}`, 500 `{error: "Session check failed"}`. These go into `components.responses` and are referenced, not repeated.

**Security schemes** (3, not 1 as in the official spec):

```yaml
bearerAuth:   { type: http, scheme: bearer, bearerFormat: JWT }
apiKeyBearer: { type: http, scheme: bearer, description: "API key prefixed with tmx_, same Authorization header" }
cookieAuth:   { type: apiKey, in: cookie, name: jwt }
```

One extra header to document as an optional global parameter: the admin impersonation header (`ADMIN_TARGET_USER_HEADER` in `auth-manager.ts`, resolve the constant's value), which swaps `req.userId` and can respond 403 `IMPERSONATION_NOT_ALLOWED` / 404 `TARGET_USER_NOT_FOUND` / 423 `TARGET_DATA_LOCKED`.

**Path parameters**: each `:name` in the path becomes `parameters[in: path, required: true]`. The type comes from how `req.params.name` is consumed in the handler: `Number(req.params.x)` (19 occurrences) and `parseInt(req.params.x)` (4) become `integer`; plain `as string` or direct use becomes `string`. Unused: `string`.

**Query parameters**: collect every `req.query.X` (84 accesses) and `const { a, b } = req.query`. Type by coercion: `Number(...)`/`parseInt` becomes integer/number; `=== "true"` becomes boolean; `as string` becomes string; comparison against a string literal (`=== "all"`) becomes enum. `required` only when the handler answers 400 on absence (`if (!x) return res.status(400)`); otherwise `required: false`. Default comes from `const { limit = 50 } = req.query` or `?? 50`.

**Headers**: collect `req.headers["name"]`, `req.get("Name")`, `req.header("Name")` (54 accesses). Each becomes `parameters[in: header]`, `required: false`, with a note on its effect when it can be inferred (e.g. a `User-Agent` starting with `Termix-Mobile/` or `X-Electron-App: true` makes `/users/login` return `token` in the body).

### Phase 3: request body

First determine the **content type**, from the middleware chain and from how the handler consumes the body:

| Signal | Content type | Schema |
|---|---|---|
| default (every app has `express.json`/`bodyParser.json`) | `application/json` | object derived from `req.body` |
| `upload.single("field")` in the chain (multer, `memoryStorage`) | `multipart/form-data` | `field: {type: string, format: binary}` + remaining fields. Confirmed Termix pattern: a `data` field holding serialized JSON (`JSON.parse(req.body.data)`), so the schema of `data` is the same JSON object as the file-less variant. Emit both content types on the same operation. |
| handler uses `Busboy` / `req.pipe(bb)` (`file-manager/content-routes.ts`) | `multipart/form-data` | fields from `bb.on("field", ...)` and `bb.on("file", ...)` |
| handler reads `req.body` as a `Buffer` or `req.on("data")` without multer, on an app with `express.raw({type: "application/octet-stream"})` | `application/octet-stream` | `{type: string, format: binary}` |
| `bodyParser.urlencoded` + handler without JSON | `application/x-www-form-urlencoded` | rare; treat as plain JSON |

**JSON body schema.** Sources, in order, all merged:

1. **Destructuring** `const { a, b = default, c } = req.body` (313 `req.body` accesses in total). Each key becomes a property. Default present: `default` + not required.
2. **Direct accesses** `req.body.x`, `body.x` when `const body = req.body`.
3. **Cast** `req.body as Partial<X>` / `as X`: use the whole type `X` through the type checker (only 4 occurrences, but when present it is the best source).
4. **Manual validation** sets required flag and type: `isNonEmptyString(x)` followed by `return res.status(400)` becomes `required`, `type: string`; `typeof x !== "number"` becomes number; `Array.isArray(x)` becomes array; `!x` followed by 400 becomes required; `["a","b"].includes(x)` becomes enum.
5. **Coercion** sets the type: `Number(x)`, `parseInt(x)` become integer; `!!x` becomes boolean; `JSON.stringify(x)` before writing to a `text` column becomes object/array (the item type comes from the matching `JSON.parse` in the response transformer, Phase 4).
6. **Cross-check with `src/types`**: when the set of destructured keys overlaps heavily (>70%) with an `interface`/`type` in `src/types/index.ts` (e.g. the ~95 keys of `POST /host/db/host` against `HostData`), use the interface's types to fill `type`/`enum`/`nullable` of the properties and record `x-matched-type: HostData`. String enums such as `authType: "password" | "key" | "credential" | "none" | "opkssh" | ...` only exist there.
7. **Cross-check with the frontend client** (Phase 7) confirms or contradicts; a contradiction becomes a warning in the report.

A key with no type hint at all stays `{}` (any) with `x-confidence: unknown`; it is never invented.

Confirmed special case: `POST /host/db/host` and `/host/enroll` share a handler but `/enroll` passes the body through `applyHostEnrollmentDefaults` first; document the difference in `description` and keep both `paths`.

### Phase 4: responses

This is the phase where the official spec fails the most (98.4% of responses without a schema). For each handler, walk the whole body (including helper functions called with `res` as an argument) and collect **every** exit point, not just the happy path:

| Pattern | Status | Content type | Schema |
|---|---|---|---|
| `res.json(expr)` | 200 (or the `res.status(N)` chained before it) | `application/json` | type of `expr` (below) |
| `res.status(N).json(expr)` | N | `application/json` | same |
| `res.status(N).send()` / `res.sendStatus(N)` | N | none | empty |
| `res.send(string \| Buffer)` | 200 | `text/html` if the expr is `renderHtml(...)`, `text/plain` if string, `application/octet-stream` if Buffer, or the nearest `res.setHeader("Content-Type", ...)` / `res.type(...)` value | string/binary |
| `res.setHeader("Content-Disposition", "attachment; ...")` + `res.send`/`res.write`/pipe | 200 | `application/octet-stream` (or the Content-Type set) | `format: binary`, `Content-Disposition` header documented |
| `res.sendFile(...)` | 200 | by extension | binary |
| `res.redirect(url)` / `res.redirect(302, url)` | 302 | none | `Location` header |
| `res.writeHead(200, {"Content-Type": "text/event-stream"})` + `res.write("data: ...")` | 200 | `text/event-stream` | see SSE below |

Status codes found in the tag (as a sanity check for the extractor): 200, 201, 202, 302, 400, 401, 403, 404, 408, 409, 413, 423, 429, 500, 502, 503.

**Type of `expr`** (this is where ts-morph earns its keep):

1. **Object literal** (`res.json({ success: true, hosts })`): schema property by property. Boolean/string/number literals become `const`. An identifier becomes the type of its symbol. Counts in the tag: `success` 64 times as the first key, `message` 37, `ok` 12, `error` hundreds.
2. **Identifier or call** (`res.json(result)`, `res.json(await repo.listFolders(userId))`): `checker.getTypeAtLocation(expr)`, unwrap `Promise<>`, serialize the type to JSON Schema. When the type resolves to `XRecord = typeof table.$inferSelect`, emit `$ref: #/components/schemas/XRecord` (generated in Phase 5). Arrays become `items`.
3. **Call to a known transformer**: apply the transformation to the input schema instead of trusting the return type (which is `Record<string, unknown>` and says nothing):
   - `transformHostResponse(h)`: the `tags` column (CSV text) becomes `string[]`; `tunnelConnections`, `jumpHosts`, `quickActions`, `socks5ProxyChain`, `portKnockSequence` become arrays (JSON.parse); `statsConfig`, `terminalConfig`, `dockerConfig`, `proxmoxConfig`, `proxmoxStatsConfig`, `guacamoleConfig` become objects or absent; every `enable*`/`show*`/`pin`/`ignoreCert` becomes boolean; `sshPort`/`rdpPort`/`vncPort`/`telnetPort` become integers with defaults. Item types come from `src/types` (`TunnelConnection`, `JumpHost`, `QuickAction`, `ProxmoxConfig`, ...).
   - `stripSensitiveFields(h)`: remove `SENSITIVE_FIELDS` (resolve the constant), remove `terminalConfig.sudoPassword`, add `hasKey`, `hasKeyPassword`, `hasPassword`, `hasSudoPassword`, `hasRdpPassword`, `hasVncPassword`, `hasTelnetPassword` as booleans.
   - `sanitizeHostForRecipient`: projection onto `CONNECT_LEVEL_FIELDS` (resolve the `Set`).
   - Others (`serialize`, `toPublicSettings`, `formatCredentialOutput`, `serializeCrontab`): use the declared return type; if it is `Record<string, unknown>`, mark `x-confidence: low` and list it in the report for manual handling.

   Keep this transformer table in a generator config file, not hardcoded, because it grows with each version.
4. **`.map(transform)`** over an array: apply the item above to the element type.
5. **Spread** `{ ...transformHostResponse(row), extra }`: merge.

**Multiple responses with the same status**: `oneOf` with a `description` per branch (e.g. `/users/login` 200 has the `requires_totp` shape and the full-login shape, and in the latter `token` is optional, conditioned on a header). When all branches are `{error: string}` with different strings, collapse into one schema and list the messages under `x-error-messages`.

**Standard error**: `{ error: string, code?: string, details?: string }`. The catalog of `code` values, extracted from every `code: "CONST"` (25 distinct in the tag: `SESSION_EXPIRED`, `TOTP_REQUIRED`, `DATA_LOCKED`, `CONTAINER_NOT_FOUND`, `SUDO_REQUIRED`, `API_KEY_REQUIRED`, ...), goes into `components.schemas.ErrorCode` as an enum.

**SSE** (3 confirmed endpoints: `GET /ssh/tunnel/status/stream` on the tunnel service, `GET /proxmox/discover/stream` on the main one, the chat in `ai/`): a `200` response with `text/event-stream`, plus an `x-sse-events` extension listing each distinct `event:` and the schema of `data:` (type of the `JSON.stringify` argument inside `res.write`). The `: keepalive` heartbeat every 30s is documented in `description`. The reference client is `src/ui/api/sse-stream.ts`.

### Phase 5: Drizzle schema becomes `components.schemas`

Read every `sqliteTable("name", { ... })` in `schema.ts` (72 tables). Mapping:

| Drizzle | JSON Schema |
|---|---|
| `text("c")` | `string` |
| `text("c", { length: 8192 })` | `string`, `maxLength` |
| `integer("c")` | `integer` |
| `integer("c", { mode: "boolean" })` (62 columns) | `boolean` |
| `integer("c", { mode: "timestamp" })` | `string`, `format: date-time` |
| `real("c")` | `number` |
| `varchar` (1, dialect-only) | `string` |
| missing `.notNull()` | `type: [T, "null"]` |
| `.default(v)` | `default: v` (skip `sql\`CURRENT_TIMESTAMP\``, only annotate) |
| `.primaryKey({ autoIncrement: true })` | `integer`, `readOnly: true` |
| `.references(() => t.col)` | `x-references: "t.col"` |
| a `text` column that some transformer `JSON.parse`s | keep `string` in `XRecord` (that is what the database holds); the transformed schema (Phase 4) switches it to object/array |

Schema name: the `*Record` exported by the repository when it exists (`HostRecord`, `SnippetFolderRecord`, ...), otherwise `<TablePascalCase>Record`. Keep `x-table: "ssh_data"` for traceability (the `hosts` table is called `ssh_data` in the database).

Sensitive fields (`password`, `key`, `keyPassword`, `sudoPassword`, `totpSecret`, `passwordHash`, `clientSecret`, ...) never reach the client because of `stripSensitiveFields`/`toPublicSettings`; the raw `XRecord` stays in `components` only as a derivation base, marked `x-internal: true`, and what operations reference is the sanitized version.

### Phase 6: cross-checking with the test suite produces `examples`

For each file in `tests/database/routes/*.test.ts` and `tests/hosts/**`:

1. Identify the route under test: the tests locate the handler with `router.stack.find(layer => layer.route.path === "/x" && layer.route.methods.post)`. Extract path + method from that `find`.
2. Extract the mocked `req` (`body`, `params`, `query`, `headers`) into request `examples`.
3. Extract the assertions `expect(res.statusCode).toBe(N)` and `expect(res.body).toEqual({...})` / `toMatchObject({...})` into response `examples` for status N. `toMatchObject` becomes a partial example (`x-partial: true`).
4. A divergence between the schema inferred in Phase 4 and the test example becomes an error in the report (the test is right).

Where an assertion uses a variable instead of a literal, resolve it through the file's own `vi.hoisted(() => ({...}))` when possible; otherwise skip.

### Phase 7: cross-checking with the frontend client

For each exported function in `src/ui/main-axios.ts` and `src/ui/api/*.ts`:

1. Find the call `instance.get|post|put|patch|delete("/path", body?, config?)`. Resolve the instance to a base URL/service (instances are created by a factory taking `baseURL`; map by `baseURL` or by name: `authApi`, `sshHostApi`, `tunnelApi`, `fileManagerApi`, `statsApi`, `dashboardApi`, `dockerApi`, ...).
2. Template-literal paths (`` `/host/db/host/${id}` ``) normalized to `{id}`.
3. The `body` type (function parameter) and the `Promise<T>` return compared with Phases 3 and 4. Agreement raises confidence; disagreement becomes a warning. When Phase 4 ended in `unknown` (a response passed through from an external library, e.g. Docker), the frontend type is used as the schema with `x-confidence: frontend-type`.
4. Transport details (`headers: {"Content-Type": "multipart/form-data"}`, `responseType: "blob"`, `withCredentials`) confirm the content types from Phases 3/4.

### Phase 8: reusing text from the existing `@openapi` comments

Run the same YAML parser `swagger-jsdoc` uses over the 425 blocks and, per (path, method), take only `summary`, `description`, `tags` and `parameters[].description`. Never copy `requestBody`/`responses` from there. A route without a block gets a `summary` generated from file name + method and `tags` from directory/file (`database/routes/snippets.ts` becomes `Snippets`; `hosts/metrics/managers/cron.ts` becomes `Host Metrics`).

### Phase 9: emitting OpenAPI 3.1

Structure:

- `info`: `title: Termix API (unofficial, generated)`, `version: <tag>`, `x-termix-source: {tag, commit, generatedAt, generator}`.
- `servers`: one per service, with `url: http://localhost:<port>` and `x-termix-service`; each operation repeats `servers` with its own (OpenAPI allows per-operation `servers`).
- `paths`: key is the final path with `{param}`. Operation with `operationId` = `<service>_<method>_<path slug>`, stable across versions (e.g. `database_post_host_db_host`). `x-source: {file, line}`. `x-shared-handler` when applicable.
- `components.securitySchemes`: the 3 from Phase 2. Default `security` is `[{bearerAuth: []}, {apiKeyBearer: []}, {cookieAuth: []}]`; public routes override with `[]`.
- `components.schemas`: `XRecord` (Phase 5), transformer-derived schemas (`HostResponse`, `HostConnectLevelResponse`), named request bodies when shared (`CreateHostBody` referenced by `/host/db/host` and `/host/enroll`), `Error`, `ErrorCode`.
- `components.responses`: `Unauthorized`, `AdminRequired`, `DataLocked`, `InternalError` (the generic 500 `{error}`).
- `x-websocket-endpoints`: a list with `url` (`ws://localhost:30002/`, `ws://localhost:30003/ssh/tunnel/c2s/stream`, `30009`, `30011`), auth (query `?token=` / `?shareToken=` as in `hosts/terminal/index.ts`), and the message protocol as far as it can be extracted from the `JSON.parse(message)` + `switch (msg.type)` in the `ws.on("message")` handler. A first version may only list the URLs and the auth type.
- Everything the extractor could not type carries `x-confidence` (`test` > `repository-type` > `handler-literal` > `frontend-type` > `matched-type` > `inferred` > `unknown`) so the SDK generator can decide between a strong type and `dict[str, Any]`.

### Phase 10: validation and report

Criteria for a successful generation (the script fails if any is not met):

1. `unresolved` is empty and the route count is within 2% of the raw count of `X.METHOD(` calls in the code (in the tag: 476).
2. No route without at least one documented 2xx/3xx response.
3. Spec valid under `@redocly/cli lint` (or `swagger-parser validate`).
4. Every route in the official spec exists in ours (the `official - ours` diff is empty); the reverse is the known gap (~80) and goes into the report.
5. Zero unresolved conflicts between test examples (Phase 6) and inferred schemas (Phase 4).

Report (`spec/report.md`, generated): counts per service, `x-confidence` distribution, list of `unknown` responses, unmapped transformers, warnings from the frontend cross-check, and the diff against the official spec. This report is what tells us where manual reading is worth the time.

**Live instance** (optional, later): start it from the repo's own `docker/`, log in with an API key, hit a sample of idempotent `GET`s and validate the real JSON against the generated schema. Mainly useful to close the Docker/Proxmox `unknown`s.

## Known limitations and how each one is handled

| Limitation | Impact | Handling |
|---|---|---|
| `strict: false` in the backend: `req.body` is `any`, many returns are `Record<string, unknown>` | Phase 3 and part of Phase 4 rely on syntactic analysis, not the type checker | Already planned: coercions + validators + cross-check with `src/types` and the frontend. Where none of that reaches, `x-confidence: unknown` and no invention. |
| Responses passed through from external libraries (Docker Engine API, Proxmox, Guacamole) | `unknown` schema | The frontend (Phase 7) usually types them; otherwise a live instance; otherwise `dict[str, Any]` in the SDK |
| Handlers delegating `res` to a helper (`sendError(res, ...)`, `respondWith(res, ...)`) | hidden responses | Phase 4 follows calls that receive `res` as an argument, up to depth 3; one specific wrapper (`managerHandler()`, used by 30 routes) is modeled explicitly rather than generically, since it never passes `res` through to its per-route callback at all |
| `router.use(path, fn)` catch-all routes | ambiguous method | emit with `x-any-method: true`; inspect the handler to narrow it when it checks `req.method` |
| Order of `app.use(auth)` vs route registration decides whether a route is public | needs position in the file | Phase 1 records `line`; Phase 2 compares it with the line of the global `app.use` |
| WebSocket message protocol | outside OpenAPI | first version only lists URL and auth; the protocol gets its own document |
| The spec changes with every Termix release | drift | the generator is re-runnable; `report.md` diffed between tags shows what changed (new/removed routes, new fields) |

## Implementation status

The generator is written and committed under `tools/spec-gen/` (Node + TypeScript + ts-morph, run with `npm --prefix tools/spec-gen run generate -- --tag <tag>`). Run from scratch (shallow clone + `npm ci --ignore-scripts` + the full pipeline, including the extra `npm run generate:openapi` build for Phase 10's official diff) against `release-2.7.1-tag`: about 1m30s end to end (skip the official diff with `--skip-official-diff` to drop that to ~50s), `unresolved: 0`, 0 opaque handlers, 0 lint errors. Output in `spec/`: `termix-routes-ir.json` (Phase 1), `termix-drizzle-ir.json` (Phase 5), `termix-analysis-ir.json` (Phases 2-4), `termix-test-examples.json` (Phase 6), `termix-frontend-crosscheck.json` (Phase 7), `termix-openapi.json` (Phase 9, also carries Phase 10's `x-official-spec-diff`), `report.md` (Phase 10).

Implemented and tested against the real tag:
- **Phase 0** (`clone.ts`): resolves the latest release via the GitHub API, shallow-clones it, runs `npm ci --ignore-scripts`. Also accepts `--repo <path>` to reuse an existing checkout during development.
- **Phase 1** (`routes.ts`): an origin-resolution graph (`express()`/`Router()`) built through TypeScript's own symbol resolution, following function parameters across files — including 2-level chains like `registerManagerRoutes` → `registerCronRoutes` — via `findReferencesAsNodes()`. This correctly disambiguates the confirmed name collision between the two different `registerTailscaleRoutes` functions in different files, because resolution follows the real imported binding at each call site, never the identifier's text.
- **Phase 5** (`drizzle.ts`): all 72 tables, with a tie-break heuristic (shortest name) for tables that have multiple `*Record` aliases across different repositories (e.g. `hosts` has 5 aliases — `HostRecord`, `FleetMemberHostRecord`, etc. — and the heuristic correctly picks `HostRecord`).
- **Phases 2-4** (`handler-analysis.ts`, combined into one module): auth (including a cross-file line-number comparison bug, found once real data was run through it, for routes registered via `registerXRoutes` outside the service's root file — now fixed), path/query/header parameters, request bodies (including the `let body; if (multipart) {...} else { body = req.body; }` idiom used by `POST /host/db/host`, only caught after extending alias detection past plain `const` initializers to plain assignment expressions), and responses (including `oneOf` for `/users/login`'s two 200 shapes, merging conditional/`||` branches instead of falling back to a generic union type, and a dedicated case for the `managerHandler()` wrapper that wraps 30 routes in `hosts/metrics/managers/*.ts` without ever exposing `res` to the per-route callback).
- **Phase 6** (`tests-examples.ts`): rather than reverse-engineering each hand-rolled `req`/`res` mock (which differs from file to file), extraction leans on a convention confirmed to hold across a good chunk of the suite: a `describe("METHOD /path", () => {...})` block's title *is* the route, Express syntax and all. From there, `expect(x.statusCode).toBe(N)` and `expect(x.jsonBody | x.body).toEqual(...)`/`.toMatchObject(...)` are read straight off their own call arguments — no need to know how `x` was built. Run against the real tag: **90 examples**, covering 29 routes across 7 test files. Examples land in `termix-openapi.json` as `examples` on `requestBody`/`responses`, and when a test confirms a status Phase 4 never found, it's added to the spec with `x-confidence: "test"` instead of being dropped.
- **Phase 7** (`frontend-client.ts`): cross-checks every `xApi.get/post/put/patch/delete(path, body?, config?)` in `src/ui/main-axios.ts` and `src/ui/api/*.ts` against a route. The non-obvious part: the axios instances (`hostApi`, `sshHostApi`, ...) are `export let xApi: AxiosInstance;` with no initializer, assigned later via `xApi = createApiInstance(getApiUrl(prefix, PORT), "LABEL")` inside an init function — so resolving `sshHostApi.post(...)` back to a service means finding that assignment, not the declaration's own initializer. Two real bugs only surfaced once this ran against the actual tag: (1) `sshHostApi = hostApi;` is a bare alias to a *different* instance, not a `createApiInstance` call — needed fixed-point alias resolution; (2) the path prefix baked into the instance itself (`getApiUrl("/host", 30001)`) was never being prepended to each call's own literal path, so every route behind an instance with a non-empty prefix (`hostApi`/`sshHostApi`, `tunnelApi`, `fileManagerApi`, `dockerApi`, `homepageApi`) matched no route at all — fixing that alone took matched calls from 300 to 377 (then to 380, once the Phase 1 path-prefix fix — see criterion 4 below — brought in 3 new metrics routes that also have a frontend call). Run against the real tag: **380 calls matched, covering 354 of 494 routes** (72%). When Phase 4 found no response schema (`x-confidence: unknown`) but the frontend has a concrete return type (`Promise<SSHHost>`, etc.), that type — marked `x-confidence: "frontend-type"` — fills the gap; the same applies to the request body when the backend only does `...req.body` without destructuring anything by name. The cross-check also **found two real Phase 3 bugs** during development: `req.body ?? {}` (instead of plain `req.body`) wasn't recognized as a request body at all, silently dropping all 5 of `POST /automations`'s fields to zero; both are now fixed.
- **Phase 9** (`openapi.ts`): emits a full OpenAPI 3.1 document, folding in Phase 6's examples and Phase 7's gap-filling.
- **Phase 10** (`validate.ts`): a report with counts, confidence distribution, opaque handlers, routes with no success response, Phase 6/7 coverage, and a real `@redocly/cli lint` pass against the output.

- **Phase 8** (`jsdoc-text.ts`): the 425 existing `/** @openapi ... */` blocks are real YAML (the same thing `swagger-jsdoc`, behind the official spec, parses), and `@openapi` is recognized by TypeScript's own JSDoc parser as an ordinary custom tag — `tag.getComment()` hands back the YAML body already stripped of the `/** * */` framing, no hand-rolled comment parser needed. Each block's key (`/path/{param}: method:`) already comes in full OpenAPI form, matching the same `pathKey` Phase 9 already builds from `route.path` — so no per-file correlation is needed, just a key match. Run against the real tag: **425 blocks parsed with zero failures**, and **345 of 491 operations** (excluding catch-alls) got a real `summary`/`description`/`tags` instead of the generated heuristic. `requestBody`/`responses` from these blocks are never used as a schema source — only prose (`summary`, `description`, `tags`, `parameters[].description`), exactly as decided earlier.

- **Phase 10, criterion 4** (`official-diff.ts`): rather than scraping `docs.termix.site/api/termix-api` (a Docusaurus site that bakes the spec into static HTML at *its own* build time, with no stable raw-JSON URL to fetch), the diff runs `npm run generate:openapi` — the same command Termix itself uses to produce the official spec — inside the clone the generator already has, and compares the result. Run against the real tag: **413 official operations, 410 matched** what we generated. Of the 3 left over, **all 3 turned out to be errors in the official docs, not gaps in our extraction**: `GET/DELETE /host/opkssh/token/{hostId}` (the `@openapi` comment is missing the `/ssh/` segment — the real registered path is `/host/ssh/opkssh/token/{hostId}`) and `GET /automations/runs` (the `@openapi` comment documents it without a suffix, but the registered route is `/automations/runs/history` — the same finding already noted in an earlier, private coverage audit as "undocumented," except it turns out the official spec *does* have an entry for it, just at the wrong path). The diff also **found and fixed a real Phase 1 bug**: `registerHostMetricsViewerRoutes` is called from two call sites (one direct, with the default `"metrics"` prefix; one through `registerProxmoxStatsRoutes`, which overrides it to `"proxmox-stats"`) — `pathPrefix` resolution only ever looked at the *first* call site it found, so `/metrics/heartbeat`, `/metrics/register-viewer`, and `/metrics/unregister-viewer` were missing entirely. Fixed by generalizing `resolveStringLiteral` to return every value it can resolve to (a fan-out), not just one — the route count went from 491 to 494 from that fix alone.

With this, all 10 of Phase 10's validation criteria and all 8 extraction phases are implemented and verified against the real tag. Nothing from the original design is left outstanding.

## Real completeness: how many routes, and how much of each is typed

"The tool runs end to end" is not the same claim as "every route is 100% documented on both sides." Exact numbers from the run against `release-2.7.1-tag`, taken from `spec/report.md` and `spec/termix-openapi.json` itself:

| Metric | Result |
|---|---|
| `paths` in the final OpenAPI document | 395 |
| Operations (method+path pairs) | 491 |
| Catch-all routes (`x-any-method-routes`, outside `paths`) | 3 |
| Total routes discovered | 494 |
| Handler resolved (not opaque) | 494/494 |
| At least one success response documented | 490/494 |
| **Response fully typed** (zero `unknown` at any depth) | 327/494 (66%) |
| **Request body fully typed** (POST/PUT/PATCH routes, every field with a concrete type, at any depth) | 150/265 (57%) |
| **Both sides fully typed at once** | 252/494 (51%) |

A note on the response numbers: an earlier draft of this document reported 395/494 (80%) and 215/494 (44%) for the first two. Recounting with a fixed script instead of a manual count (to measure the request-body work below precisely, before/after) gives 327/494 (66%) for responses under the strict "zero `unknown` at any depth, recursive" rule — that's a difference in counting method, not a regression: response generation did not change a single line in this round of work (the response confidence numbers in `report.md` are byte-identical before and after everything below). The request-body number, on the other hand, genuinely moved: it was 25/265 (9%) under this same strict rule before the work below, and is 150/265 (57%) after it.

The request body used to drag the average down the most, and by design: the extractor almost always got **which fields exist** right (destructuring and `req.body.x` access are cheap to find), but only assigned a field a **concrete type** when it found explicit evidence in the code — `isNonEmptyString(x)`, `Number(x)`, an enum comparison, and so on. A field with no such signal was deliberately left `x-confidence: unknown`, because the rule since the very first draft of this document has been to never invent a type without proof in the source. A follow-up round of work closed most of that gap with six additive strategies, each only ever touching a field that was still `unknown`: the type of a destructuring default literal, a type declared via `req.body as {...}`, more validator/coercion patterns recognized in the handler's own code, matching a field's name against the Drizzle column it's stored in, matching against a `src/types/index.ts` interface, and merging in the frontend HTTP client's own request type. Together they moved the operational metric `report.md` now tracks directly (top-level fields of the `application/json` variant) from **34/265 (13%) to 183/265 (69%)**.

Decision: responses keep the same typing approach as before (out of scope for this round). Document the exact request-body number honestly rather than chase 100%, and revisit if a real consumer of the spec (the Python SDK generator) turns out to need a specific field that's still untyped.
